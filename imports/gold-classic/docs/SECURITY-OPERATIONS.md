## 1. SIEM — التغذية والتصدير (§20)

### المصدر
كل الأحداث الحساسة مسجلة في `AuditLog` (سجلات غير قابلة للتعديل، محمية بـ `audit:read`/`audit:export`). الأحداث العملياتية لمشتريات/مبيعات/ثقة في `ErpAuditTrail` وتنعكس في `AuditLog` عبر `writeErpAudit()`.

### نقطة التصدير

```
GET /api/v1/audit/export/siem?since=<ISO>&severity=<INFO|WARNING|CRITICAL>&entityType=&action=&format=<ndjson|cef>&limit=<1..5000>
```

- **التفويض**: `audit:export` — منصّة فقط.
- **التنسيقان**:
  - NDJSON (`application/x-ndjson`): سطر واحد لكل حدث، بنية ECS-مستوحاة (`event`, `observer`, `actor`, `source`, `correlation`).
  - CEF (`text/plain`): `CEF:0|JOHAR|gold-platform|1.0|<signature>|<msg>|<severity>|rt=... src=... suser=... act=...`.
- **رؤوس إضافية**: `X-SIEM-Export-Count` (عدد الصفوف)، `X-SIEM-Format`.
- **التلقين**: سحب دوري (driver بجلسة 10 دقائق أو CIDR) مع احتفاظ بآخر `since` كـ cursor لتجنب التداخل.

### الأحداث المعيارية
`*_APPROVE`, `*_REJECT`, `KYB_*`, `TRUST_FACTOR_*`, `HITL_*_REVIEW`, `SOD_CONFLICT`, `AUTH_*`, `CUSTODY_*`, `PAYMENT_*` تلحق تلقائياً درجة CRITICAL لتمييزها في التنبيهات.

## 2. النسخ الاحتياطي والتعافي من الكوارث Backup / DR (§20)

### طبقات النسخ
| الطبقة | الأداة | التكرار | RPO | RTO |
|---|---|---|---|---|
| قاعدة المعاملات | Neon — نسخ زمنية لفورية (PITR) | مستمر | ≤ دقيقة | ≤ 15 دقيقة |
| المفريّ المتقطع | `pg_dump` عبر نقطة الإدارة | كل 6 ساعات | ≤ 6 ساعات | ≤ 30 دقيقة |
| خارج الموقع | نسخة مفريّ مضغوطة مشفرة إلى تخزين كائنات منفصل (S3/Blob) | يومي (UTC 02:00) | ≤ 24 ساعة | ≤ 4 ساعات |
| الأهبة | كود (git) + وظائف Netlify (ترقيم إصدارات تلقائي) | كل نشر | — | إعادة بناء فورية |

### إجراء الاستعادة
1. `prisma db push` → إنشاء مخطط نظيف.
2. `pg_restore` أحدث مفريّ سليم → تحقق `SELECT count(*) FROM audit_logs`.
3. تجاوب: عدم تطابق المخطط → نسخة PITR أقدم مع ترحيل تصاعدي.
4. التحقق من السجلات: تشفير، نسخ احتياطي للأسرار (ENCRYPTION_KEY/NEON URL) في مدير أسرار منفصل — **لا تُدرج أسرارٌ في المستودع**.

### حقوق الوصول
النسخ الاحتياطية حساسة: وصول الوحدة الأمنية فقط، وصول القراءة عبر نقطة محددة بـ IP، والوصول للتدمير مقيد بدورين.

## 3. اختبار الاختراق Penetration Testing (§20)

| البند | القيمة |
|---|---|
| التكرار | نصف سنوي (أو عند أي إصدار معماري فرعي: مصفوفة صلاحيات، شريحات ERP/Trust) |
| النطاق | كل نقاط `/api/v1` المغطاة في `GET /api/v1/openapi.json` + بوابة Netlify |
| الحالات الإلزامية | تجاوز ABAC (org→org)، SoD cross-role، رفع Tier عبر trust، مصادقة/MFA، تسريب أسرار في الاستجابات |
| المعايير | 0 ثغرات CRITICAL/HIGH كشرط خروج؛ أي HIGH يفتح حادثة IR |
| الأدوات | إطراف خارجي معتمد + إعادة فحص دورية بالأدلة من `openapi.json` |

> السجل المرجعي: فتحة `trust:evaluate` (module غير منصة) كشفتها اختبارات حيّ وسُدَّت بنقلها إلى وحدة `compliance` — نموذج يُستخدم في حالات اختبار لكل نشر.

## 4. خطة الاستجابة للحوادث Incident Response (§20)

### خطوات الاستجابة (IR Playbook)
1. **الاكتشاف** (#مستوى CRITICAL في SIEM / تنبيه الفريق / بلاغ مستخدم).
2. **التصنيف**: Severity 1–4 حسب التأثير (بيانات معرَّضة، خرق صلاحيات، إتلال خدمة، احتيال).
3. **الاحتواء**: إبطال خاص بالمستخدم/المفتاح، تجميد حساب/مؤسسة، عزلة وظيفة.
4. **التحري**: سجلات `AuditLog` + `ErpAuditTrail` + `BlockchainEvidence` (بلا تغيير) + PITR snapshot.
5. **الاستئصال**: إصلاح الجذر، تصحيح + نشر مغلق، تحديث السجل (PermissionRegistry).
6. **التعافي**: استعادة/تحقق من النسخ، إعادة عرض من أسرار جديدة.
7. **الدروس المستفادة**: تقرير بعد الحادث، تحديث المصفوفة/الوثيقة، إضافة حالة اختبار دائمة.

### الادوار
| الدور | المسؤولية |
|---|---|
| Incident Commander | تنسيق + قرارات Severity 1/2 |
| Security Lead | الاتجار التقني للمصدر جذر |
| Ops | نشر الإصلاحات، تحويل البيئة |
| Comms / Legal | إخطار الجهات (تنظيمي) والمستخدمين المتأثرين |

### خطة الإبلاغ
- Severity 1/2: تكرار فوري (≤4 ساعات) داخلياً، إجراءات محددة بين الجهات حسب القانون المعمول به.
- Severity 3/4: ضمن دفتر SLO الأسبوعي.
